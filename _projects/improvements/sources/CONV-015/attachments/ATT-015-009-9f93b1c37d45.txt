 O–P. Marginal contribution + ablation (the anti-bloat engine)

 The evaluation question is NEVER "is X useful" — it is "does adding/replacing X beat the incumbent configuration" on: unique material defects found · task completion · holdout delta · false positives · context/token cost · latency · monetary cost · reliability · security/authority cost. REJECT is a first-class outcome ("quality benefit negligible, +80% tool calls, +25% context → REJECT"). Ablation: periodically (retro-triggered, or when context budgets strain) run the incumbent package minus one component per arm (A+B+C vs A+B+D...) on frozen cases → identify REDUNDANT/CONTRADICTORY/STALE/CONTEXT-EXPENSIVE members → removal proposals with REMOVED-ledger rows. Target: minimum sufficient high-performance configuration — cleaner as well as smarter. (The kanon-kostnadsvakten + bibliotekarien are the existing embryos; this gives them an experimental teeth.)
